Capabilities are the declarations that communicate to your agent harness what a node needs in order to run. When you assign a skill to an agent node, you are not installing that skill — you are documenting a requirement so that the harness, the skill file, and the operator reading the compiled artifact all have a shared understanding of what must be available. Capability declarations travel with the artifact; every compiled Markdown file lists them explicitly, and every code module exposes them as inert data.

## Four Capability Types

Each `agent`, `evaluate`, and `tool` node can declare up to four capability sets:

| Type | Purpose | Examples |
|------|---------|---------|
| `skills` | Named responsibilities the agent needs — drawn from the capability catalog for your selected target. | `implementation`, `evaluation`, `research`, `software-architecture` |
| `tools` | Primitive tool identifiers the node requires. | `read`, `edit`, `search`, `execute` |
| `connectors` | External service connections or OpenRouter profiles the node needs access to. | `mcp:github`, `mcp:postgres`, `api:openrouter/google/gemini-2.5-flash-image` |
| `permissions` | Declared permission requirements that your harness should verify before running the node. | `workspace-write`, `read-only` |

All four sets are stored in LGIR as part of the node definition. They are included verbatim in the compiled artifact.

## Customizations

Every skill or connector you assign to a node resolves to a `customizations` record stored in the LGIR YAML. Each customization has two fields:

- **`template`**: the pre-built base contract this entry extends (e.g., `implementation-base`). If you choose a custom identifier not in the catalog, it starts from a safe generic skill or connector contract.
- **`instructions`**: editable text you write to narrow the skill's scope for this specific node (e.g., *"Focus on the specified module only. Do not modify test files."*).

You can edit customization instructions directly in the inspector. All customizations are persisted in LGIR, so compiled artifacts are fully reproducible and do not depend on hidden studio state.

```yaml
capabilities:
  skills:
    - implementation
    - test-design
  tools:
    - read
    - edit
  connectors:
    - mcp:github
  permissions:
    - workspace-write
  customizations:
    implementation:
      template: implementation-base
      instructions: "Focus on the specified module only. Do not modify test files."
```

## Capability Report

After a successful compilation, the compiler emits a **capability report** alongside the artifact. It classifies every workflow construct the target encountered:

| State | Meaning |
|-------|---------|
| `native` | The target handles this construct mechanically and without approximation. |
| `instructional` | The target expresses this as explicit instructions — the harness is told what to do, but there is no runtime enforcement by the compiler. |
| `unsupported` | The target cannot handle this construct. Always produces an error diagnostic. |

For Markdown targets (codex, claude, hermes), constructs like `approval` gates, `loop` bounds, and declared connector availability are reported as `instructional` — the generated skill file tells the agent what to do, but it is not a machine-enforced contract. For code targets (python, typescript), the native capabilities are typed workflow data, stable topological order, dependency maps, and pure readiness helpers.

<Note>
Catalog entries are authoring suggestions, not an inventory of installed capabilities. Ladder Graph does not connect to your agent harness, inspect your configuration, install skills, grant permissions, import runtime packages, or invoke connectors. It produces a text artifact that documents what is needed — your harness and your operators are responsible for providing it.
</Note>
